## 从根源减少模型调用失败：prompt 瘦身 + 输出预算调整 + 提交数上游收口

### 问题根源（已确认）

模型调用失败的主因不是超时太短，而是 **prompt 过大**：
1. 每个 atom 的 `files` 列表无上限——单个大 commit 改 500 个文件就塞 500 条路径
2. `evidenceRefs` 里每个文件路径重复一遍（`file:src/...`），同一个路径在 prompt 里出现两次
3. `diffHints` 重复 `commit=<subject>`，而 `atom.title()` 已经有 subject
4. 没有任何 prompt 大小预估 / 截断——80 个 atom × 30 文件可达 ~96K tokens，远超 DeepSeek 64K 上下文
5. 每次调用固定预留 `max_tokens=8000` 输出，64K 上下文只剩 56K 给输入
6. range scan（`base..head`）无 `--max-count`，cursor 过期时可能返回大量提交

### 修改方案（6 处，都是最小改动）

#### 1. `WorkSessionScanService.AtomAccumulator.toAtom()` — 每个 atom 文件数收口
- `files` 列表在**发给模型**时截断到最多 15 个（`atom.files()` 仍保留完整列表给 validator 和 affectedFiles 持久化，只是 prompt 里不全部铺开）
- `diffHints` 去掉冗余的 `commit=<subject>`（title 已有），只保留 `files=` 前 8 个路径摘要

#### 2. `ModelSegmentEnricher.prompt()` — prompt 瘦身 + 大小防护
- 每个 ATOM 行：`files=` 只取前 15 个路径 + `+N more`；`evidence=` 只发 `commit:<hash>` 不发逐个 `file:` 路径（validator 仍用完整 evidenceRefs 校验，prompt 不需要全量）；`diffHints` 去掉 `commit=` 前缀
- 新增 `estimatePromptChars()` 估算，超过阈值（约 45000 字符 ≈ 15K tokens）时对 atom 列表截断或切到 RULE_GROUP 模式
- `MAX_OUTPUT_TOKENS` 从 8000 降到 4000（8 段 × 500 tokens 足够），给输入留更多空间

#### 3. `ProjectCapabilityService.modelDrafts()` — 能力分析 prompt 瘦身
- 每个 SEGMENT 行的 `evidence=` 只发前 10 个证据引用（不全部铺开）
- `plainSummary` 截断到 200 字符

#### 4. `PendingChangeScanService.prepare()` — range scan 加 `--max-count` 安全阀
- `base..head` 范围扫描加 `--max-count=120`（正常范围扫描不会超，但 cursor 过期时防止失控）

#### 5. `ModelGatewayService` — 请求体优化
- 把 `MAX_OUTPUT_TOKENS` 的控制权交给调用方（enricher 传 4000，capability 传 4000，文件分析保持原值）

#### 6. 测试更新
- 更新 `ModelSegmentEnricherTest` / `DevelopmentSegmentationServiceTest` 适配新的 prompt 结构
- 新增测试验证大 atom 列表不会撑爆 prompt

### 不改的部分
- `evidenceRefs` 完整列表仍保留在 atom 对象里（validator 需要）
- `affectedFiles` 完整列表仍持久化（证据细节区需要）
- 超时配置保持 240 秒（上一轮已改，合理）
- 失败分类器保持（上一轮已加，仍有用）
