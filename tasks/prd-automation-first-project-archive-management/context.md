# 上下文与现状

## 当前产品方向

ProjectFlow 是本地优先的开发者工作台，核心价值不是管理任务列表，而是把真实项目活动转成可审查、可追溯、可复用的工程资产。

当前主流程：

1. 导入项目材料。
2. 生成项目画像。
3. 绑定本地项目路径。
4. 开发后刷新变化。
5. 基于 Git evidence / Evidence Bundle 生成候选变更。
6. 审查候选变更。
7. 采纳后进入项目档案、成长记录、每日回顾和成果输出。

## 现有问题

### 1. 长期记录页面仍像普通列表

成长时间线、字段来源链、待确认档案、档案变化、分析记录等入口已经拆出，但页面还没有形成长期管理能力：

- 缺少月份、日期、类型、状态筛选。
- 缺少按时间组织的长条卡片。
- 缺少进入完整详情后的上下文回退。
- 缺少对 3 个月以上数据量的展示策略。

如果只继续堆列表，后续记录越多，越不适合开发者回看项目成长。

### 2. 首页重复显示同类信息

首页的今日变化闭环和最近活动都在展示候选变更、文件变化、审查入口。重复会造成两个问题：

- 用户不知道哪个区域是主流程。
- 页面空间被重复卡片占用，项目画像和下一步动作被弱化。

首页应该只承担“当前该做什么”的工作台职责，历史记录和完整细节应进入独立页面。

### 3. 审查页仍然偏手工填报

结构化变更详情页和项目档案页目前仍使用大量 textarea，让用户手工补技术决策、经验沉淀、成果素材。这个设计偏离自动化管理：

- 用户完成审查前需要阅读和填写太多内容。
- AI/规则生成的候选价值没有作为主视图呈现。
- “采纳后到底改变了什么”反馈不够强。

正确方向是：系统生成候选，用户审查确认，必要时修正。

## 可复用现有基础

- 项目画像与文件理解已经有导入分析基础。
- Evidence Bundle 已能生成候选变更。
- 采纳变更已能写入项目档案和来源链。
- 多个长期入口页已经存在，可在现有路由上改显示方式。
- 右侧入口和独立详情页已经初步建立，不需要重做大框架。

## 设计约束

- 不大改 UI 布局，只改信息组织、交互重点和页面内容层级。
- 优先复用现有实体、接口和页面，不新建大批服务。
- 每个长期列表都必须支持老数据管理，不只为当天数据服务。
- 自动化总结失败时，必须保留本地规则摘要和人工修正入口。
- 所有确认动作必须可追溯来源，不能把 AI 输出直接当正式档案。
