# V3.2 项目画像最终版改进计划

日期：2026-06-20

对象：ProjectFlow 项目画像、架构与文件理解、杂乱项目导入分析

参考项目：`C:\Users\Administrator\Documents\Codex\综测系统.zip`

## 一句话结论

ProjectFlow 的项目画像应该从“文件识别工具”升级为“开发者项目理解地图”。

它既要能把 `综测系统` 这种杂乱测试包整理清楚，也要能把标准前后端分离、传统前后端一体、单体后端、脚本工具、桌面端、移动端、数据/AI 项目展示得有条理。

最终目标不是展示更多文件，而是回答开发者最关心的五个问题：

1. 这个项目是做什么的。
2. 怎么启动、入口在哪里。
3. 核心业务代码在哪里。
4. 哪些是依赖、配置、测试、运行产物或噪声。
5. 下一步应该先看哪里、改哪里、验证哪里。

## 对当前截图总结的评价

截图中的 `综测系统` 总结已经明显比之前好，方向正确，原因是它做到了三点：

1. 说清楚了项目用途：学生综测材料上传与审核。
2. 说清楚了主要技术路径：单页 HTML、Python 服务、本地 OCR、SQLite。
3. 说清楚了重要限制：测试包版本、不含真实学生数据、OCR 本地化、未接入 AI。

但它还有优化空间。

### 当前略显啰嗦的地方

现在顶部总结和模型分析卡片存在内容重复：

- 顶部说了一遍“前端单页 HTML、后端 Python、RapidOCR、SQLite”。
- 模型分析卡片又说了一遍“frontend html、tools server、scorecard_batch/ocr.py、output db、start_server”。

这不是错误，但阅读成本偏高。项目画像第一屏应该更像“工程摘要”，不要把路径细节全部塞进自然段。

### 建议改成两层表达

第一层：顶部画像摘要，只保留业务、架构、状态。

示例：

```text
综测系统是一个本地运行的学生综测材料上传与审核原型。前端是单页 HTML 审核台，后端是 Python 内置 HTTP 服务，OCR 通过本地 RapidOCR 完成，审核记录写入 SQLite。当前更像测试包而非标准工程，已包含启动脚本、核心 OCR/身份解析模块和本地运行数据，但 vendor、output 与临时目录需要从源码画像中折叠。
```

第二层：模型分析卡片，展示结构化事实，不再写长段落。

示例：

```text
入口：start_server.bat / start_server.ps1 -> tools/scorecard_upload_server.py
前端：frontend/scorecard-upload-prototype.html
核心：scorecard_batch/ocr.py、identity.py、models.py
数据：output/scorecard_upload.db 为运行产物
依赖：requirements.txt、requirements-ocr.txt、vendor/
风险：RapidOCR 依赖缺失会导致识别失败；output 不应进入源码管理
```

这样既不丢信息，也更适合开发者快速判断。

## 通用项目画像框架

项目画像不应该按“前端/后端”二分，因为很多真实项目不是这种结构。应该先按“开发职责”建模，再映射到具体技术栈。

### 一级画像

每个项目都尽量抽取以下信息：

| 画像字段 | 说明 | 示例 |
| --- | --- | --- |
| 项目用途 | 解决什么业务或开发问题 | 综测材料上传审核、本地 OCR 原型 |
| 项目形态 | 工程类型 | 前后端分离、前后端一体、单体后端、脚本工具、桌面端、移动端、数据/AI 项目 |
| 启动入口 | 开发者如何跑起来 | `start_server.bat`、`main.py`、`npm run dev`、`mvn spring-boot:run` |
| 运行架构 | 请求、页面、服务、数据如何流动 | HTML -> Python HTTP -> OCR -> SQLite |
| 核心模块 | 真正业务逻辑在哪里 | `scorecard_batch/`、`src/main/java/.../service` |
| 配置与依赖 | 环境、依赖、构建、部署 | `requirements.txt`、`package.json`、`pom.xml`、`docker-compose.yml` |
| 测试与验证 | 怎么验证功能 | `tests/`、`src/test/`、`pytest`、`mvn test` |
| 运行产物 | 数据库、上传目录、构建产物 | `output/`、`.db`、`dist/`、`target/` |
| 外部依赖噪声 | 应折叠的内容 | `vendor/`、`node_modules/`、`.venv/` |
| 当前风险 | 开发和维护风险 | 依赖缺失、无测试、配置不完整、数据混入源码 |
| 下一步建议 | 最应该做的工程整理 | 补启动说明、折叠 output、拆分核心模块 |

### 二级文件角色

文件角色需要覆盖所有常见开发项目，而不是只覆盖标准前后端项目。

| 文件角色 | 命中对象 | 适用项目 |
| --- | --- | --- |
| 前端入口 | `src/app/page.tsx`、`App.vue`、`index.html`、`frontend/*.html` | 前端、全栈、原型包 |
| 后端入口 | `main.py`、`app.py`、`Application.java`、`server.js`、`Program.cs` | 后端、全栈、脚本服务 |
| 服务入口 | `tools/*server*.py`、`server.py`、`api.py` | 工具型项目、临时服务 |
| 路由/控制器 | `controller/`、`routes/`、`views.py`、`router` | Web 后端、传统 MVC |
| 业务服务 | `service/`、`domain/`、`usecase/`、`core/` | 后端、单体、领域项目 |
| 数据模型 | `models.py`、`entity/`、`schema/`、`dto/` | 后端、数据项目、AI 项目 |
| 数据访问 | `repository/`、`mapper/`、`dao/`、`prisma/` | 后端、单体、全栈 |
| 前端组件 | `components/`、`views/`、`pages/` | 前端、全栈 |
| 样式资源 | `.css`、`.scss`、`assets/` | 前端、桌面端、移动端 |
| 脚本工具 | `scripts/`、`tools/`、`.bat`、`.ps1`、`.sh` | 所有项目 |
| 依赖配置 | `package.json`、`pom.xml`、`requirements*.txt`、`pyproject.toml`、`go.mod`、`Cargo.toml` | 所有项目 |
| 构建配置 | `vite.config`、`next.config`、`webpack.config`、`build.gradle` | 前端、后端、全栈 |
| 运行配置 | `.env.example`、`application.yml`、`config/` | 所有项目 |
| 部署配置 | `Dockerfile`、`docker-compose.yml`、`nginx.conf`、`k8s/` | 后端、全栈、部署项目 |
| 测试文件 | `tests/`、`src/test/`、`*.test.*`、`*_test.py` | 所有项目 |
| 文档证据 | `README*`、`docs/`、说明 `.md/.html` | 所有项目 |
| 数据脚本 | `migrations/`、`.sql`、`seed` | 后端、数据项目 |
| AI/模型资产 | `models/`、`.onnx`、`.pt`、`prompts/`、`notebooks/` | AI、OCR、数据项目 |
| 运行产物 | `output/`、`.db`、`tmp/`、`upload_*`、`logs/` | 所有项目 |
| 外部依赖 | `vendor/`、`node_modules/`、`.venv/`、`target/`、`dist/` | 所有项目 |

这个角色体系可以覆盖：

- 标准前后端分离项目。
- 传统前后端一体项目。
- Spring Boot / Django / Laravel / Rails 这类单体项目。
- Electron / Tauri / 桌面工具。
- Android / iOS / Flutter / React Native。
- Python 脚本工具和本地原型包。
- 数据处理、OCR、AI 模型项目。
- 只有后端或只有前端的项目。

## 传统前后端一体项目如何适配

传统一体项目不要强行拆成 frontend/backend。应该按技术框架识别“页面层、控制器、服务、模板、静态资源、数据层”。

### Java / Spring MVC / JSP / Thymeleaf

应展示为：

- 页面模板：`templates/`、`webapp/`、`*.jsp`
- 控制器：`controller/`
- 业务服务：`service/`
- 数据访问：`repository/`、`mapper/`
- 实体模型：`entity/`、`domain/`
- 配置：`application.yml`、`pom.xml`
- 测试：`src/test/`

### Django / Flask

应展示为：

- 应用入口：`manage.py`、`app.py`
- 路由/视图：`urls.py`、`views.py`
- 模型：`models.py`
- 模板：`templates/`
- 静态资源：`static/`
- 配置：`settings.py`、`requirements.txt`
- 测试：`tests/`

### Laravel / Rails

应展示为：

- 路由：`routes/`
- 控制器：`controllers/`
- 模型：`models/`
- 模板：`views/`
- 数据迁移：`migrations/`
- 配置：`.env.example`、`composer.json`、`Gemfile`

核心原则：前后端一体项目不是“没有前端”，而是前端页面被模板、静态资源和后端路由共同承载。

## 有条理项目的展示方式

对结构清晰的项目，ProjectFlow 应该“尊重原结构”，不要过度重组。

示例：标准 `frontend/` + `backend/` 项目。

展示方式：

1. 顶部画像：一句话说明业务、技术栈、阶段。
2. 架构卡片：前端、后端、数据库、部署关系。
3. 模块列表：沿用真实模块，例如 `frontend`、`backend`、`docs`、`scripts`。
4. 文件列表：按模块筛选，标注入口、服务、配置、测试。
5. 风险卡片：缺测试、缺部署配置、敏感配置、模型调用失败等。

有条理项目不需要强行改名，只需要补充“职责标签”和“阅读顺序”。

## 杂乱项目的展示方式

对 `综测系统` 这种项目，ProjectFlow 应该“重建秩序”，不要原样展示混乱路径。

- `vendor/`：大量第三方 Python 依赖。

- `scorecard_batch/identity.py`、`models.py`、`ocr.py`：核心 OCR 和身份解析逻辑。

- `start_server.bat`、`start_server.ps1`、`启动.bat`：启动脚本。

### 应该输出的画像

```text
综测系统是一个本地运行的学生综测材料上传与审核原型。前端是单页 HTML 审核台，后端是 Python 内置 HTTP 服务，OCR 通过本地 RapidOCR 完成，审核记录写入 SQLite。当前更像测试包而非标准工程；ProjectFlow 已折叠 vendor、缓存、二进制依赖和运行输出，开发者应优先查看 README、启动脚本、服务入口、前端原型和 scorecard_batch 核心模块。
```

## 项目画像文案规则

### 顶部总结规则

顶部项目画像最多 4 句。

建议结构：

1. 第一句：项目用途。
2. 第二句：运行架构。
3. 第三句：当前工程状态。
4. 第四句：关键限制或下一步。

不要在顶部堆太多路径。路径应进入结构化分析卡片。

### 模型分析卡片规则

模型分析卡片不要写成第二篇长总结。它应该更像事实表：

- 入口
- 前端
- 后端/服务
- 核心模块
- 数据
- 依赖
- 风险
- 证据

### 文件列表规则

文件列表不是越全越好，而是要能管理开发。

每个文件至少要显示：

- 文件角色
- 开发优先级
- 是否可修改
- 是否运行产物
- 是否外部依赖
- 为什么重要

## 后端分析规则改进计划

### P0：增加文件角色分类器

在 `ProjectIntelligenceService` 和 `project-insights.ts` 中统一文件角色规则。

必须新增或修正：

- `requirements-ocr.txt` -> 依赖配置。
- `README_TEST_PACKAGE.html` -> 文档证据。
- `scorecard_upload.db` -> 运行产物 / 数据库。
- `tools/scorecard_upload_server.py` -> 服务入口。
- `frontend/scorecard-upload-prototype.html` -> 前端原型。
- `scorecard_batch/` -> 核心业务包。
- `vendor/` -> 外部依赖噪声。
- `output/` -> 运行产物。

### P0：增加项目形态识别

新增 `projectShape`，至少包含：

- `FRONTEND_BACKEND_SPLIT`
- `FULLSTACK_MONOLITH`
- `BACKEND_ONLY`
- `FRONTEND_ONLY`
- `SCRIPT_TOOL`
- `DESKTOP_APP`
- `MOBILE_APP`
- `DATA_OR_AI_PIPELINE`
- `LOCAL_PROTOTYPE_PACKAGE`
- `UNKNOWN`

`综测系统` 应识别为：

```text
LOCAL_PROTOTYPE_PACKAGE + DATA_OR_AI_PIPELINE
```

### P0：增加入口识别

入口识别优先级：

1. 显式启动脚本：`start*`、`run*`、`.bat`、`.ps1`、`.sh`
2. 服务入口：`server.py`、`main.py`、`app.py`、`Application.java`、`server.js`
3. 前端入口：`index.html`、`page.tsx`、`App.vue`
4. README 中声明的启动命令

### P1：增加噪声统计

导入时应记录：

- 总文件数。
- 展示文件数。
- 折叠 vendor 数。
- 折叠缓存数。
- 折叠二进制/运行产物数。
- 折叠原因。

这能解释为什么一个 3830 文件项目最后只展示 14 个核心开发信号。

### P1：增加阅读顺序生成

按以下顺序生成：

1. README / docs
2. 启动脚本
3. 应用入口
4. 路由/控制器
5. 核心业务服务
6. 数据模型/数据访问
7. 前端页面/组件
8. 测试
9. 配置/部署
10. 运行产物，仅最后展示

### P1：模型 prompt 改造

项目分析 prompt 必须要求模型返回：

```json
{
  "summary": "项目用途和状态",
  "projectShape": "项目形态",
  "runtimeArchitecture": "运行架构",
  "entrypoints": [],
  "coreModules": [],
  "developerReadingOrder": [],
  "runtimeArtifacts": [],
  "externalDependencies": [],
  "risks": [],
  "cleanupSuggestions": [],
  "evidence": [],
  "limitations": []
}
```

这样模型输出才能稳定地服务 UI，而不是每次生成风格不同的长段落。

## 验收标准

### 标准项目

导入 ProjectFlow 或 insightwrite-2.0 这类结构较清晰项目时：

- 能识别前端、后端、配置、文档、测试。
- 不把 `.git`、`.codex-run`、构建产物当作业务模块。
- 顶部总结清楚但不啰嗦。
- 文件列表按模块和角色展示。

### 传统一体项目

导入 Spring MVC、Django、Laravel、Rails 等项目时：

- 不强行拆成 frontend/backend。
- 能识别模板、静态资源、控制器、服务、模型、数据访问。
- 能说明页面和后端在同一个工程内。

### 杂乱项目

导入 `综测系统` 这类项目时：

- 能明确项目是本地原型包 / 测试包。
- 能折叠 vendor、缓存、二进制、运行产物。
- 能识别启动脚本、服务入口、前端原型、核心 OCR 模块。
- 能给出建议阅读顺序。
- 能显示“为什么只展示这些文件”。

## 最终目标

ProjectFlow 对项目画像的判断标准应该是：

> 不是“我看到了多少文件”，而是“我能不能让开发者在 3 分钟内知道这个项目怎么运行、核心代码在哪里、哪些文件该忽略、下一步该怎么整理和开发”。

这才是项目画像对开发者最重要的管理价值。
