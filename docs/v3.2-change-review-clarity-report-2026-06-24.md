# ProjectFlow V3.2 变更审查与项目档案清晰度改进报告

> 日期：2026-06-24  
> 范围：变更审查详情、项目档案入口、分析记录、长期记录导航、文件路径展示、前端体积统计  
> 核心目标：让用户 7 天、30 天后回看时，先看到“我到底做了什么”，再按需进入证据、文件和测试细节。

## 1. 当前判断

这一轮问题不是单个页面排版问题，而是 ProjectFlow 的信息优先级再次偏回了“技术证据展示”。

当前页面已经具备证据包、结构化变更、项目档案、成长时间线、字段来源链和分析记录，但用户看到的主信息仍然大量是：

- Evidence Bundle
- backend / frontend
- 文件数量、行数
- affected files
- test evidence
- build evidence
- sourceType / status
- 长路径和长 Markdown

这些信息对系统可信度有价值，但不应该成为第一层阅读内容。第一层必须回答：

1. 这轮开发实际改了什么功能或体验？
2. 这个变化对项目档案的哪个部分有影响？
3. 用户是否已经确认？
4. 确认后在哪里继续看到它？
5. 如果需要追溯，完整证据入口在哪里？

## 2. 代码事实

### 2.1 变更标题和摘要仍偏技术来源

当前 `EvidenceDraftChangeService` 生成候选变更时：

- 标题使用 `Evidence Bundle 候选变更：` 加任务意图或分支名。
- 摘要使用 `基于 Evidence Bundle 生成的保守候选：x 个文件，+x/-x 行，归因 x，置信度 x。`
- 细节直接来自 `objectiveEvidence`。
- 影响文件直接保存完整文件列表。

结果是前端只能展示“文件和证据”，很难展示“用户到底改了什么”。

### 2.2 详情页把长内容放在当前页展开

当前 `project-changes/[changeId]` 页面：

- 顶部标题和卡片标题重复。
- `EvidenceCard` 使用 `<details>` 在页面内展开长内容。
- `影响文件`、`测试证据`、`构建证据` 与核心变更摘要同级展示。
- 用户想知道改动本身，却被文件路径、测试描述和构建描述抢占注意力。

### 2.3 长期记录列表仍在列表页展开详情

当前 `ResourceTimeline`：

- 每条记录是 `<details>`。
- 点击后在列表内部展开 `detail`。
- 虽然有 `打开完整页`，但详情仍会把列表撑长。

这会让成长时间线、分析记录、档案变化等长期页面在数据变多后变得臃肿。

### 2.4 项目档案入口仍展示过长摘要

当前 `project-intelligence` 的分析记录入口：

- `分析记录` 卡片会展示最近记录摘要。
- 如果摘要较长，入口本身就变成内容展示区。

入口页应该只显示数量、最新时间、类型和进入按钮，不应该直接展示长摘要。

### 2.5 前端体积异常来自依赖和构建产物

当前本地目录体积统计：

| 区域 | 大小 |
| --- | ---: |
| frontend | 508.63MB |
| backend | 8.08MB |
| .git | 3.51MB |
| other | 1.12MB |

`frontend` 内部：

| 目录 | 大小 |
| --- | ---: |
| node_modules | 374.6MB |
| .next | 132.13MB |
| public | 1.43MB |
| src | 0.37MB |
| tests | 0.02MB |

结论：前端 99% 不是源码膨胀，而是 `node_modules` 和 `.next` 被统计进项目体积。ProjectFlow 的项目扫描、zip 导入和画像展示必须默认把这些目录视为运行产物，不应该作为项目源码价值的一部分展示。

## 3. 改进原则

### 3.1 第一层只展示结论

变更审查、项目档案入口、分析记录列表、成长时间线列表的第一层只展示：

- 中文标题
- 一句话变化
- 类型
- 时间
- 状态
- 影响到的项目档案字段
- 进入详情按钮

不展示长路径、不展示原始 Markdown、不展示测试全文、不展示构建全文。

### 3.2 大而杂内容必须进入独立页

以下内容不允许在摘要页用下拉框展开：

- 完整文件路径列表
- 完整 Git evidence
- 完整分析记录详情
- 完整测试证据
- 完整构建证据
- 原始 Agent Result
- 原始项目材料摘要

摘要页只提供入口，例如：

- 查看完整证据
- 查看影响文件
- 查看分析详情
- 查看来源材料
- 查看档案写入记录

### 3.3 变更审查要从“文件变化”改为“开发成果入库”

核心展示顺序改为：

1. 用户做了什么。
2. 为什么系统这样判断。
3. 会写入项目档案哪里。
4. 是否有风险或缺少验证。
5. 完整证据在哪里。

文件路径只作为证据索引，不作为主叙事。

### 3.4 已采纳内容必须有后续归宿

采纳后不能只提示“已写入项目档案”。必须在项目档案入口中形成可追溯记录：

- 成长时间线：增加一条“本次确认的变化”。
- 字段来源链：对应字段显示来源为“已采纳变更”。
- 档案变化：记录哪个字段变了。
- 输出来源：成果输出能引用这条确认事实。

用户从变更审查采纳后，应该能在项目画像右侧入口看到数量变化，并能点进去找到该条记录。

## 4. 信息架构调整

### 4.1 变更审查列表

目标：列表只负责筛选和快速判断，不承载完整审查。

每条候选变更展示：

```text
[类型] [影响级别] [待确认]
中文标题
一句话说明用户改了什么
将写入：已完成能力 / 技术决策 / 风险 / 成果素材
关键文件 2 个 · 更多文件进入详情
按钮：完整审查 / 采纳 / 忽略
```

不再展示：

- Evidence Bundle 英文标题
- commit message 原文作为主标题
- 文件路径预览长串
- 行数作为主信息

### 4.2 变更审查详情页

目标：详情页是“项目资产入库台”，不是证据堆放页。

页面结构：

```text
返回上一步
结构化变更详情

主卡片：
  中文标题
  用户实际改动摘要
  采纳状态
  写入去向

入库预览：
  已完成能力：修复 zip 导入大小限制
  技术决策：上传上限和扫描读取预算分离
  当前风险：缺少真实大 zip 回归样本时标记为待复测
  成果素材：可写入 README 的本地项目导入能力说明

审查判断：
  是否可采纳
  是否缺测试
  是否缺构建
  是否需要人工修正

证据入口：
  完整文件列表
  Git evidence
  测试证据
  构建证据
  原始来源

操作：
  采纳
  忽略
  修正 AI 总结
```

当前页不再内联展开长证据。证据入口跳转到独立页或同一路由的 `?tab=evidence` 视图。

### 4.3 证据详情独立页

新增或改造：

```text
/project-changes/[changeId]/evidence
```

页面承载：

- 影响文件完整列表，支持搜索和模块分组。
- Git evidence 原文。
- 测试证据。
- 构建证据。
- 来源材料。
- 返回结构化变更详情。

这个页面可以长，因为用户是主动进入追溯模式。

### 4.4 项目档案入口

目标：右侧入口列只做导航，不展示长内容。

入口卡片统一格式：

```text
成长时间线      12 条    最新 06-24 14:17    查看
字段来源链       5 项    已确认 5 项          查看
待确认档案       0 条    无待确认             审查
档案变化         1 条    最新 06-24 14:17    查看
分析记录         1 条    最新项目分析         查看
```

不再展示：

- 最近分析记录全文
- 长项目定位摘要
- 文件路径
- Markdown 片段

### 4.5 成长时间线

目标：按时间管理项目变化，帮助用户回看项目成长。

列表第一层展示：

- 日期
- 中文标题
- 变化类型
- 写入字段
- 一句话摘要

点击后进入详情页，不在列表内展开。

### 4.6 分析记录

目标：分析记录是历史资料库，不是摘要堆叠区。

列表只展示：

```text
项目分析 / 文件分析
创建时间
一句话摘要，最多 2 行
来源：模型 / 本地规则
按钮：查看详情
```

完整分析内容只在：

```text
/project-analysis-records/[recordId]
```

### 4.7 文件路径展示规则

所有路径展示统一遵守：

- 第一层最多展示 2 到 3 个关键路径。
- 长路径使用中间压缩，例如 `backend/.../ProjectZipUploadGuard.java`。
- 完整路径列表进入独立页。
- 路径必须可复制。
- 文件列表需要按模块分组：前端、后端、文档、配置、测试、运行产物。
- `node_modules`、`.next`、`target`、`dist`、`build`、`.git`、`.codex-run` 默认作为运行产物或噪音，不进入关键文件列表。

## 5. 后端生成策略

### 5.1 候选变更需要生成中文业务摘要

`EvidenceDraftChangeService` 不应只生成文件统计。它至少要产出：

- `title`：中文变更标题。
- `summary`：用户实际完成了什么。
- `details`：变化依据和模块影响。
- `affectedFiles`：完整路径列表，作为证据而不是标题来源。
- `decisionNotes`：是否形成技术决策。
- `riskNotes`：是否有风险或缺验证。
- `assetCandidates`：是否可进入周报、README、简历素材。

本地规则无法理解业务语义时，也要使用更清晰的保守表达：

```text
调整 zip 导入限制与错误提示，让 90MB 到 244MB 的本地项目 zip 可以正常进入导入流程，并避免把上传过大误报为服务断连。
```

而不是：

```text
基于 Evidence Bundle 生成的保守候选：10 个文件，+111/-24 行。
```

### 5.2 文件变化只作为证据维度

文件变化仍要保存，但展示上降级为：

- 涉及模块
- 关键文件数量
- 是否包含测试
- 是否包含配置
- 完整文件入口

### 5.3 采纳后生成可追溯入库事件

采纳 ProjectChange 后，应保证：

- ProjectMemory 更新。
- ProjectFactSource 记录字段来源。
- ProjectEvolutionRecord 记录成长事件。
- 档案变化页能看到本次变化。
- 成果输出能引用该条记录。

如果某个环节没有数据，页面必须显示“未生成”，不能假装已连接。

## 6. 前端实施阶段

### Phase 1：去掉摘要页长展开

范围：

- `ResourceTimeline`
- `project-intelligence`
- `project-intelligence/analysis-records`
- `project-intelligence/timeline`
- `project-intelligence/changes`

要求：

- 移除列表内 `<details>` 展开长内容。
- 卡片改为摘要 + 查看详情。
- 长内容只进入详情页。

验收：

- 分析记录列表不会直接显示完整分析文本。
- 成长时间线不会被一条长记录撑高。
- 项目档案入口不展示长摘要。

### Phase 2：重做变更审查详情的信息层级

范围：

- `project-changes/[changeId]`
- `ChangeReviewList`
- `ChangeReviewSidebar`

要求：

- 顶部只保留一个页面标题。
- 主卡片优先展示“用户改了什么”。
- 文件、测试、构建、来源全部变成证据入口。
- 采纳去向在页面右侧或主卡片清晰展示。

验收：

- 第一屏不出现大段文件路径。
- 第一屏不出现 Evidence Bundle 英文标题作为主标题。
- 用户能在 10 秒内判断是否采纳。

### Phase 3：新增或改造证据详情页

范围：

- `/project-changes/[changeId]/evidence`
- API 类型复用 `ProjectChange`

要求：

- 完整文件列表按模块分组。
- 测试证据、构建证据、风险备注分区展示。
- 支持返回变更详情。
- 不影响原采纳流程。

验收：

- 用户点击“查看完整证据”能看到所有路径和证据。
- 摘要页不再承担完整证据展示。

### Phase 4：后端候选变更摘要升级

范围：

- `EvidenceDraftChangeService`
- 必要时新增小型摘要 helper，不新增大服务。

要求：

- 根据文件类型、路径、commit message 和 objective evidence 生成中文标题。
- 摘要聚焦“开发成果”，文件统计放在 details 或 evidence 中。
- 保守摘要也要具体，不要只写行数。

验收：

- 生成候选变更后，标题和摘要不再以 `Evidence Bundle` 开头。
- 列表第一层能看到实际变更内容。

### Phase 5：采纳后归档反馈闭环

范围：

- `ProjectMemoryService`
- `project-intelligence` 入口计数
- 成长时间线、字段来源链、档案变化页面

要求：

- 采纳后入口计数刷新。
- 档案变化页能找到该条采纳记录。
- 字段来源链能看到来源 ID 和确认状态。
- 成长时间线能按日期看到该条变化。

验收：

- 用户采纳一条变更后，不需要猜它去了哪里。
- 进入项目画像右侧入口能找到对应记录。

### Phase 6：体积和扫描噪音治理

范围：

- zip 扫描
- 项目画像文件结构
- README 或导入说明

要求：

- 明确 `node_modules`、`.next`、`target`、`dist` 等是运行产物。
- 项目画像的体积统计区分源码、依赖、构建产物。
- zip 导入和本地扫描默认忽略运行产物。

验收：

- ProjectFlow 不再让用户误以为“前端源码占 99%”。
- 文件结构重点展示源码、配置、文档、测试和入口。

## 7. 页面文案规则

### 7.1 禁用主标题表达

不要在第一层标题中使用：

- Evidence Bundle 候选变更
- UNKNOWN / MEDIUM
- EVIDENCE_BUNDLE
- PENDING
- Uncommitted working tree changes

这些可放在小标签、来源信息或证据页。

### 7.2 推荐标题表达

用中文动作和结果：

- 修复 zip 导入大小限制，避免大项目误报服务断连
- 优化项目档案入口，减少长期记录挤占首页
- 调整变更审查详情页，让采纳去向更明确
- 清理运行产物展示，项目画像只突出开发相关文件

### 7.3 摘要句模板

摘要必须像项目日志，不像 Git diff：

```text
本次调整统一了 zip 上传限制，并把超限错误改为明确中文提示。用户导入 90MB 到 244MB 的本地项目 zip 时，不会再被 64MB 或 100MB 的旧限制误拦截。
```

不使用：

```text
10 个文件，+111/-24 行，归因 UNKNOWN，置信度 MEDIUM。
```

## 8. 最终验收标准

### 8.1 独立使用验收

新用户不读文档，能完成：

```text
导入项目 -> 看到画像 -> 绑定路径 -> 开发一天 -> 回来看变化 -> 审查 -> 生成输出
```

并且每一步知道：

- 当前是什么状态。
- 下一步去哪。
- 采纳后写入哪里。
- 以后在哪里回看。

### 8.2 信息层级验收

任意列表页第一屏：

- 不展示超过 3 条长路径。
- 不展示完整 Markdown。
- 不内联展开证据长文本。
- 不把 Evidence Bundle / sourceType / status 当主标题。
- 有明确详情入口。

### 8.3 变更质量验收

每条候选变更必须能回答：

- 用户改了什么。
- 影响哪个模块。
- 是否能采纳。
- 采纳后进入哪个项目档案字段。
- 完整证据在哪里。

### 8.4 长期回看验收

30 天后用户进入项目档案，能按时间和字段找到：

- 某一天确认了哪些项目变化。
- 每个档案字段为什么变成当前内容。
- 哪些变化成为了成果输出素材。
- 哪些变化只有证据但没有采纳。

## 9. 不做事项

本轮不做：

- 不大改整体视觉风格。
- 不把 ProjectFlow 做成通用任务管理器。
- 不删除证据，只调整证据展示层级。
- 不把 AI 候选直接写成正式档案。
- 不用更多卡片堆叠代替信息架构整理。

## 10. 推荐执行顺序

1. 先改 `ResourceTimeline`，移除列表内长展开。
2. 再改项目档案入口，所有入口只显示数量、最新时间和按钮。
3. 再改变更审查详情页，让主信息聚焦“用户改了什么”。
4. 再新增证据详情页，承接所有长路径和证据。
5. 再升级 `EvidenceDraftChangeService`，从源头生成中文成果摘要。
6. 最后补采纳后归档反馈和体积噪音说明。

这个顺序的原因是：先把长内容从页面抽走，再补详情承载页，最后改后端摘要质量。否则前端会继续被低质量候选文本拖着走。
