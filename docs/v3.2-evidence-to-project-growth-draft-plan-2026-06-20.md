# ProjectFlow V3.2 证据到项目成长闭环改进计划

> 状态：Implemented baseline  
> Last Updated：2026-06-21  
> 文件路径：`docs/v3.2-evidence-to-project-growth-draft-plan-2026-06-20.md`  
> 目标：把 ProjectFlow 从“能导入、能审查、能输出”的工具，升级为“开发过程自动沉淀为可信项目资产”的开发者工作台。

## 0. 本轮执行结果

本轮已完成 V3.2 基线闭环，重点解决“用户独立用起来”的 SC-0：

- 工作台新增主流程状态机：导入项目、看到画像、绑定路径、刷新变化、生成证据包、变更审查、生成输出都有明确下一步。
- zip 导入改为“添加项目”入口，不再在已有项目时常驻占位。
- Evidence Bundle 后端响应新增 `status`、`nextAction`、`changeId`，同一 Work Session 保持一个证据包。
- 工作台新增“今日变化闭环”，把 Work Session -> Evidence Bundle -> Project Change -> Project Memory 的下一步暴露出来。
- 变更审查新增“采纳后写入”预览，说明将进入哪些项目档案字段和后续输出。
- 项目画像新增成长时间线视角，采纳后的变化能作为每日回顾、周报、README 草稿的输出来源。
- 成果输出新增“生成依据”检查，显示项目档案、成长记录、每日回顾、任务证据是否可用。
- 新增前端静态回归测试和后端 Evidence Bundle 生命周期测试。

## 1. 本轮要解决的核心问题

当前 ProjectFlow 已经具备项目导入、项目画像、Work Session 扫描、Evidence Bundle、变更审查、项目档案、每日回顾和成果输出，但主业务链路仍有明显断点：

- 用户点击“生成证据包”后，只看到一个弱提示，不知道证据包进入了哪里、后续有什么用。
- 变更审查能采纳，但“采纳后写入了哪些项目档案字段、影响了哪些输出材料”反馈不够强。
- 项目档案像一组可编辑文本框，不像一个持续成长的项目资产库。
- 每日回顾、周报、README、简历描述使用了项目数据，但用户感知不到它们和前面证据链的关系。
- Work Session、Evidence Bundle、Project Change、Project Memory、Evolution Record 这些对象存在，但概念边界没有被产品化解释清楚。
- 入口流程容易糊化：项目导入、本地路径绑定、协议写入、Agent Result 扫描、Git evidence 扫描、上下文同步混在一起，用户不知道当前应该做哪一步。
- 项目画像已经明显改善，但“从画像到后续项目管理”的链路还不够强。

本计划的改进原则是：**每一步都必须让用户知道输入是什么、动作是什么、输出去了哪里、下一步能做什么、最终能为项目资产带来什么价值。**

## 2. 产品定位升级

### 2.1 当前定位

ProjectFlow 是一个本地优先的开发者工作台，用于项目理解、Agent 结果审查、项目档案维护、每日回顾和成果输出。

### 2.2 V3.2 目标定位

ProjectFlow 应升级为：

> 一个把真实开发活动转化为可信项目资产的本地开发工作台。

核心竞争力不是“生成一段文案”，而是下面这条闭环：

```text
真实项目 / Git / Agent Result
  -> Work Session 归因
  -> Evidence Bundle 证据包
  -> Project Change 候选变更
  -> 用户审查与采纳
  -> Project Memory 项目档案
  -> Growth Timeline 成长时间线
  -> Daily Review / README / 周报 / 简历素材
  -> 后续 Agent 上下文同步
```

如果用户看不懂这条链路，ProjectFlow 就会退化成普通项目管理面板。V3.2 必须把这条链路做成产品主线。

## 3. 关键概念边界

| 概念 | 用户语言 | 系统职责 | 不应该做的事 |
|---|---|---|---|
| Project Import | 添加项目 | 用 zip 建立初始项目画像和文件结构 | 不负责真实 Git 变化追踪 |
| Local Project Path | 绑定本地项目 | 指向真实项目目录，用于 Git evidence、协议和上下文同步 | 不扫描用户主目录 |
| Work Session | 一轮开发活动 | 根据 Git / 未提交变更推断一次工作会话 | 不直接写入项目档案 |
| Evidence Bundle | 证据包 | 汇总文件、行数、Git 证据、Agent 声明 | 不代表事实已确认 |
| Project Change | 候选变更 | 把证据包转成可编辑、可采纳的结构化变更 | 不自动变成项目成就 |
| Project Memory | 项目档案 | 保存用户确认后的项目事实、能力、风险、决策、成果素材 | 不存未确认猜测 |
| Growth Timeline | 成长记录 | 展示项目从导入到每轮改进的历史演进 | 不只是普通日志 |
| Outputs | 成果输出 | 从已确认事实生成周报、README、简历、总结 | 不优先使用未确认候选 |
| Context Sync | 上下文同步 | 把已确认项目档案写回真实项目 `.projectflow/context` | 不替用户改业务源码 |

## 4. 用户主流程设计

### 4.1 首次使用流程

```text
添加项目 zip
  -> 生成项目画像
  -> 绑定真实项目路径
  -> 写入 ProjectFlow 协议
  -> 复制 Agent 规则
  -> 开始真实开发
```

必须让用户看到：

- 当前项目是否有画像。
- 是否绑定了真实项目路径。
- 是否写入过 `.projectflow` 协议。
- Agent 应该把结果写到哪里。
- 当前还缺哪一步才能开始沉淀证据。

### 4.2 日常开发流程

```text
开发者或 Agent 修改真实项目
  -> 回到 ProjectFlow 刷新变化
  -> 校正 Work Session 意图
  -> 生成 Evidence Bundle
  -> 生成候选变更
  -> 进入变更审查
```

必须让用户看到：

- 这轮变化涉及哪些模块、文件和大概规模。
- 证据来自 Git、Agent Result、手动输入还是 zip 分析。
- 证据包是否已经生成过，更新证据包会覆盖还是合并。
- 生成候选变更后去哪里查看。

### 4.3 审查与沉淀流程

```text
候选变更
  -> 用户编辑类型、影响、说明、风险、测试证据、成果素材
  -> 采纳
  -> 写入项目档案字段
  -> 写入事实来源
  -> 写入成长时间线
  -> 更新每日回顾和成果输出可用素材
```

必须让用户看到：

- 采纳后写入了哪些字段。
- 哪些字段会影响每日回顾。
- 哪些字段会影响 README / 周报 / 简历。
- 哪些信息只是证据，哪些已经成为确认事实。

### 4.4 输出与复用流程

```text
已确认项目档案 + 成长时间线 + 每日回顾
  -> 生成输出草稿
  -> 显示引用来源
  -> 用户编辑
  -> 保存为成果资产
```

必须让用户看到：

- 这份输出引用了哪些已确认变更。
- 这份输出忽略了哪些未确认候选。
- 输出能回流为成果素材，供后续复用。

## 5. 成功标准

- SC-0：一个新用户不阅读任何文档、不需要 Agent 配合，也能独立完成完整主流程：导入项目 -> 看到画像 -> 绑定路径 -> 开发一天 -> 回来看变化 -> 审查 -> 生成输出。页面必须在每一步告诉用户当前状态、下一步动作、动作结果和结果去向。这条标准优先级高于 SC-1 到 SC-10。
- SC-1：新用户能在工作台上看懂当前项目处于“未导入、未绑定、未写协议、可扫描、待审查、可输出”中的哪一个状态。
- SC-2：用户生成 Evidence Bundle 后，页面明确显示“证据包已生成、下一步生成候选变更或进入变更审查”。
- SC-3：重复点击生成或更新证据包不会造成项目档案、下一步目标、能力列表的无脑叠加。
- SC-4：变更审查页面能明确展示“采纳后写入哪里”和“会影响哪些输出”。
- SC-5：项目档案页面能展示项目成长时间线，而不是只展示静态文本框。
- SC-6：每日回顾能自动引用当天采纳的变更、证据包和风险决策，不再像模板填空。
- SC-7：成果输出能显示来源链路：项目档案字段、成长记录、每日回顾、已确认变更。
- SC-8：未确认候选不会被默认写入项目档案、上下文同步和成果输出。
- SC-9：项目导入、真实路径绑定、协议写入、扫描、同步这些入口不再混淆。
- SC-10：前后端测试能覆盖关键闭环，不只验证页面能编译。

---

## 6. 非目标

- 不把 ProjectFlow 做成通用 Kanban 或普通任务管理系统。
- 不让 AI 自动覆盖用户确认过的项目档案。
- 不强制接入某个特定模型供应商。
- 不扫描用户主目录或全局 Agent 日志。
- 不把 Evidence Bundle 当成最终事实。
- 不在 V3.2 里做团队协作、多用户权限、云同步或商业 SaaS 能力。

## 7. 阶段计划

## Phase 1：统一主链路与状态机

### 目标

把“添加项目、绑定路径、写协议、扫描、生成证据包、变更审查、输出复用”做成明确流程，而不是散落按钮。

### 主要改动

- 建立 `ProjectReadinessState` 前端派生模型。
- 工作台显示一个主状态：
  - `NO_PROJECT`：添加项目。
  - `NO_PROFILE`：项目缺画像。
  - `NO_LOCAL_PATH`：缺真实路径。
  - `NO_PROTOCOL`：未写协议。
  - `READY_TO_SCAN`：可扫描。
  - `HAS_WORK_SESSIONS`：有待生成证据包的开发活动。
  - `HAS_EVIDENCE_BUNDLES`：有证据包待生成候选变更。
  - `HAS_PENDING_CHANGES`：有候选变更待审查。
  - `READY_TO_OUTPUT`：有已确认资产可输出。
- 每个状态只展示一个主动作和最多两个次动作。
- zip 导入保留为“添加项目”独立入口，不再在已有项目时常驻。

### 重点文件

- `frontend/src/app/dashboard/page.tsx`
- `frontend/src/lib/project-selection.ts`
- `frontend/src/lib/api.ts`
- 可新增：`frontend/src/lib/project-flow-state.ts`

### 验收

- 用户刷新工作台后能直接看懂下一步。
- 选择不同项目时，主状态和本地路径不会串项目。
- 有项目时不常驻显示 zip 导入卡。
- `npm.cmd run build` 通过。
- 新增纯函数测试覆盖状态机。

---

## Phase 2：证据包生命周期产品化

### 目标

让 Evidence Bundle 从“点击后生成一条数据”变成用户能理解的证据资产。

### 主要改动

- Evidence Bundle 增加生命周期状态：
  - `DRAFTED_FROM_SESSION`
  - `READY_FOR_CHANGE`
  - `CHANGE_DRAFTED`
  - `CHANGE_ACCEPTED`
  - `ARCHIVED`
- Evidence Bundle 列表展示：
  - 来源 Work Session。
  - 证据来源类型。
  - 文件数量、增删行、代表文件。
  - 是否已经生成候选变更。
  - 是否已被采纳。
- 生成证据包按钮改成明确语义：
  - 首次：`生成证据包`
  - 已存在：`刷新证据包`
  - 已生成候选变更：`查看候选变更`
- 重复生成时采用“同一 Work Session 一个证据包”的幂等更新，不叠加项目档案。
- 新增证据包详情页或抽屉，展示：
  - 这次变化的事实证据。
  - Agent 声明。
  - 可生成哪些候选变更。
  - 下一步按钮。

### 重点文件

- `backend/src/main/java/com/projectflow/entity/EvidenceBundle.java`
- `backend/src/main/java/com/projectflow/service/ProjectIntelligenceService.java`
- `backend/src/main/java/com/projectflow/service/WorkSessionScanService.java`
- `frontend/src/app/dashboard/page.tsx`
- `frontend/src/app/work-sessions/[sessionId]/page.tsx`
- `frontend/src/lib/api.ts`

### 验收

- 同一个 Work Session 重复生成证据包只更新同一条记录。
- 证据包生成后能明确跳到候选变更生成或详情页。
- 用户能从证据包看出“还没采纳，不是最终项目事实”。
- 后端测试覆盖幂等生成和状态流转。

## Phase 3：变更审查变成“项目资产入库台”

### 目标

变更审查不再只是采纳/忽略列表，而是项目事实入库的关键工作台。

### 主要改动

- 每条 Project Change 增加“入库预览”：
  - 写入 `completedCapabilities`。
  - 写入 `inProgressCapabilities`。
  - 写入 `currentRisks`。
  - 写入 `technicalDecisions`。
  - 写入 `learnings`。
  - 写入 `assetCandidates`。
  - 生成 Dev Log 草稿或 Growth Event。
- 采纳前显示：
  - 影响字段。
  - 来源证据。
  - 输出影响：周报、README、简历、每日回顾。
- 采纳后显示：
  - 写入成功字段列表。
  - 成长时间线新增项。
  - 可立即进入“每日回顾”或“成果输出”。
- 忽略后保留来源证据，不删除 Evidence Bundle。
- 批量采纳要显示合并结果，避免重复写入同一句话。

### 重点文件

- `backend/src/main/java/com/projectflow/entity/ProjectChange.java`
- `backend/src/main/java/com/projectflow/service/ProjectIntelligenceService.java`
- `frontend/src/app/tasks/page.tsx`
- `frontend/src/lib/api.ts`

### 验收

- 采纳前用户知道会写入哪里。
- 采纳后用户看到明确反馈，而不是只有 toast。
- 重复采纳、批量采纳不会造成档案字段重复堆叠。
- 后端测试覆盖入库预览、去重和事实来源写入。

## Phase 4：项目档案升级为成长资产库

### 目标

项目档案不再只是文本区域，而是“当前画像 + 事实来源 + 成长时间线 + 输出素材”的组合。

### 主要改动

- 项目画像页分成四层：
  - 当前画像：定位、架构、阶段、能力、风险、决策。
  - 文件结构：入口、核心、运行依赖、模块。
  - 成长时间线：每次采纳、证据包、每日回顾形成的历史节点。
  - 可复用素材：README、周报、简历、复盘可引用的素材。
- 每个档案字段显示来源：
  - 用户手动。
  - zip 分析。
  - 模型分析。
  - Agent Result。
  - 已采纳变更。
- 增加“字段可信度”：
  - `confirmed`：用户确认。
  - `candidate`：候选。
  - `stale`：可能过期。
- 同步上下文时只同步 confirmed 内容。

### 重点文件

- `frontend/src/app/project-intelligence/page.tsx`
- `frontend/src/app/projects/[projectId]/files/page.tsx`
- `backend/src/main/java/com/projectflow/entity/ProjectFactSource.java`
- `backend/src/main/java/com/projectflow/entity/ProjectEvolutionRecord.java`
- `backend/src/main/java/com/projectflow/service/ProjectIntelligenceService.java`

### 验收

- 用户能看到项目档案为什么变化。
- 用户能从时间线回看项目成长过程。
- 字段来源清晰，不再像凭空生成。
- 上下文同步不会写入未确认候选。

---

## Phase 5：每日回顾和成果输出证据化

### 目标

让每日回顾、周报、README、简历描述从模板生成，升级为“基于已确认项目成长记录的输出”。

### 主要改动

- 每日回顾自动读取：
  - 当天 Work Session。
  - 当天 Evidence Bundle。
  - 当天采纳 Project Change。
  - 当天新增风险和技术决策。
- 每日回顾页面展示“今日材料来源”，用户能勾选或排除。
- 成果输出生成前展示来源面板：
  - 已确认变更。
  - 项目档案字段。
  - 每日回顾。
  - 成长时间线。
- 输出内容必须标注来源摘要。
- 输出保存后反向沉淀为 `assetCandidates` 或独立 Output Asset。
- 对 README 和简历输出做不同风格：
  - README：更工程化，强调安装、架构、功能、限制。
  - 简历：强调角色、动作、技术、结果和证据。
  - 周报：强调周期、完成、风险、下周计划。

### 重点文件

- `frontend/src/app/dev-logs/page.tsx`
- `frontend/src/app/ai-review/page.tsx`
- `backend/src/main/java/com/projectflow/service/AiOutputService.java`
- `backend/src/main/java/com/projectflow/entity/AiOutput.java`
- `frontend/src/lib/api.ts`

### 验收

- 每日回顾不再只是模板文本。
- 输出页面能解释“这份内容来自哪里”。
- 未确认候选不会进入正式输出。
- README、周报、简历三类输出风格明显不同。
- 后端或前端测试覆盖输出来源选择和未确认数据过滤。

## Phase 6：链路级反馈与空状态治理

### 目标

解决用户“点了之后不知道发生了什么”的问题。

### 主要改动

- 所有关键动作完成后，不只弹 toast，还显示可见结果区：
  - 生成证据包后：展示证据包摘要和下一步。
  - 生成候选变更后：展示候选变更入口。
  - 采纳变更后：展示写入字段和时间线更新。
  - 同步上下文后：展示写入文件列表和目标路径。
  - 生成输出后：展示来源和保存位置。
- 所有空状态都回答三个问题：
  - 为什么现在是空的。
  - 用户下一步做什么。
  - 做完后会得到什么。
- 所有按钮文案改为结果导向：
  - 不写“提交”，写“生成候选变更”。
  - 不写“同步”，写“同步已确认上下文”。
  - 不写“更新”，写“刷新证据包”或“更新项目画像”。

### 重点文件

- `frontend/src/app/dashboard/page.tsx`
- `frontend/src/app/tasks/page.tsx`
- `frontend/src/app/project-intelligence/page.tsx`
- `frontend/src/app/dev-logs/page.tsx`
- `frontend/src/app/ai-review/page.tsx`
- `frontend/src/components/ui/*`

### 验收

- 用户执行任一关键动作后，页面本体有可见反馈。
- 不依赖 toast 才知道结果。
- 空状态不再泛泛提示“暂无数据”。
- 核心页面按钮语义统一。

## Phase 7：验证、回归和文档收口

### 目标

保证主链路不是 UI 假象，而是从后端数据到前端呈现都可验证。

### 主要验证路径

- 后端：
  - Work Session 扫描。
  - Evidence Bundle 幂等生成。
  - Evidence Bundle 到 Project Change。
  - Project Change 采纳到 Project Memory / Fact Source / Evolution Record。
  - AiOutput 只使用已确认事实。
- 前端：
  - 工作台状态机。
  - 添加项目入口。
  - 证据包反馈。
  - 变更审查入库预览。
  - 项目档案时间线。
  - 每日回顾来源选择。
  - 成果输出来源展示。
- 构建：
  - `npm.cmd run build`
  - `mvn -q test`

### 文档收口

- 更新 `docs/architecture.md`，补充 V3.2 主链路。
- 更新 `docs/api-design.md`，补充 Evidence Bundle / Work Session / Growth Timeline 输出字段。
- 更新 `PROJECT_CONTEXT.md`，让未来 agent 第一眼知道 V3.2 的业务闭环。

## 8. 建议的数据模型增强

### 8.1 Evidence Bundle

建议补充字段：

- `status`
- `changeId`
- `summary`
- `lastGeneratedAt`
- `sourceHash`
- `stale`

目的：

- 防止重复生成造成叠加。
- 让用户知道证据包是否已经产生候选变更。
- 当 Git 变化更新后，提示旧证据包可能过期。

### 8.2 Project Change

建议补充字段：

- `memoryFieldTargets`
- `outputImpact`
- `acceptedAt`
- `acceptedSummary`

目的：

- 采纳前能预览影响。
- 采纳后能解释写入了哪里。
- 输出时能按影响类型筛选素材。

### 8.3 Project Evolution Record

建议补充字段：

- `eventType`
- `sourceType`
- `sourceId`
- `beforeSnapshotId`
- `afterSnapshotId`
- `visibleSummary`

目的：

- 支撑成长时间线。
- 解释项目档案变化。
- 支撑每日回顾和成果输出。

### 8.4 Output Asset

可选新增独立表，或先复用 `AiOutput`：

- `sourceChangeIds`
- `sourceEvolutionIds`
- `sourceDevLogIds`
- `qualityWarnings`
- `userEdited`

目的：

- 让输出不只是一次性生成结果，而是可追溯资产。

## 9. 页面级改造摘要

| 页面 | 当前问题 | V3.2 改造方向 |
|---|---|---|
| 工作台 | 动作多，链路散 | 做成项目状态机 + 主动作 |
| 项目画像 | 画像改善了，但成长链路弱 | 增加来源、时间线、素材层 |
| 变更审查 | 采纳去向仍不够强 | 做成项目资产入库台 |
| 每日回顾 | 容易模板化 | 引用当天证据、变更、风险、决策 |
| 成果输出 | 来源感不够 | 输出前展示来源，输出后成为资产 |
| 文件结构 | 已较可用 | 保持简洁，接入画像与输出素材 |
| 设置 | 模型配置孤立 | 说明模型只生成候选，不自动确认事实 |

## 10. 执行顺序建议

必须按以下顺序执行，避免又出现功能堆叠但流程不清：

1. 先做工作台状态机和入口治理。
2. 再做 Evidence Bundle 生命周期。
3. 再做变更审查入库预览和采纳反馈。
4. 再做项目档案成长时间线。
5. 再做每日回顾和成果输出证据化。
6. 最后做全链路验证和文档更新。

不能先改输出页面。否则输出仍然没有足够可信的数据来源，只会继续模板化。

---

## 11. 风险和约束

- 如果只改前端文案，不补后端状态字段，证据包生命周期仍然会模糊。
- 如果 Project Memory 继续只是一组长文本字段，成长过程很难被解释。
- 如果 AiOutput 继续只读取任务、日志、已确认变更，输出来源仍然偏粗。
- 如果不做幂等和去重，重复点击仍会污染项目档案。
- 如果模型输出直接进入档案，会破坏“用户确认事实”的产品底线。
- 如果每个页面都各自解释流程，会产生重复说明；应由共享状态和共享组件统一解释。

## 12. 最小可交付版本

如果需要先做一个小但有效的 V3.2-MVP，建议只做以下 4 件：

- 工作台状态机：用户知道下一步。
- Evidence Bundle 幂等状态：用户知道证据包在哪里。
- 变更审查入库预览：用户知道采纳后写入哪里。
- 项目档案成长时间线：用户知道项目如何成长。

这四件完成后，ProjectFlow 的核心竞争力会明显增强；每日回顾和成果输出再接入这条链路，价值会自然变强。

---

## 13. 完成定义

V3.2 不能以“页面改好看了”作为完成标准。完成标准是：

- 用户可以独立说清 ProjectFlow 的主流程。
- 用户知道每个按钮的结果和下一步。
- 证据包、变更、档案、时间线、输出之间有可追溯关系。
- 任何正式输出都能说明来源。
- 未确认事实不会污染项目档案。
- 重复操作不会造成档案重复堆叠。
- 新 agent 读取本计划后可以按阶段执行，不需要重新猜产品方向。
