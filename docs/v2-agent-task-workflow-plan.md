# ProjectFlow V2 Agent Task Workflow Plan

## 目标

把 ProjectFlow 从“手动维护项目管理页面”调整为“开发者真实工作流的项目状态层”。

核心原则：

- 项目管理页就是项目的主工作台，项目档案、资料、任务、开发日志入口都应该围绕当前项目展开。
- 任务看板不应该要求用户大量手动填写，而应该优先接收 AI 和 agent 工作过程产生的任务建议、状态变化、风险、决策和日志。
- ProjectFlow 不替代 Codex、Cursor、Claude Code 这类 agent；它负责沉淀项目上下文、生成 agent 可用的工作说明，并把 agent 完成后的结果回写成可确认的项目状态。
- 所有自动化更新先进入“待确认建议”，不直接覆盖真实任务状态，避免 AI 误写项目管理数据。

## 我的判断

你提到的方向是对的：项目档案不需要单独变成一个用户反复寻找的页面，它应该自然出现在“项目管理”里面。开发者进入 ProjectFlow 的第一步通常不是创建一个漂亮的项目名，而是导入或绑定一个真实项目文件夹，然后围绕这个项目做分析、拆任务、执行、回写和复盘。

任务看板也不应该做成传统管理系统里的手动 CRUD。真正有价值的是：ProjectFlow 能根据项目资料和 agent 工作结果自动生成任务草案、任务状态变更、子任务、风险和开发日志，然后用户只做确认、调整和拒绝。

所以 V2 下一步不应该继续扩展“总览式大卡片”，而应该先打通这个闭环：

1. 导入完整项目资料。
2. AI 形成项目档案和初始任务建议。
3. 用户选择一个任务。
4. ProjectFlow 生成给 agent 使用的工作说明。
5. 用户在 agent 里完成真实开发工作。
6. agent 产出结构化工作总结。
7. ProjectFlow 导入总结，生成任务更新和开发日志建议。
8. 用户确认后，项目管理页变成新的真实状态。

## 低成本实现路线

优先选择最低成本、低依赖、少假演示的方案：先用“可复制的 Agent 工作说明 + Agent 结果导入”，暂时不做复杂插件、浏览器扩展、GitHub App 或常驻本地服务。

### 第一阶段：复制粘贴闭环

ProjectFlow 在任务旁提供“生成 Agent 工作说明”按钮，输出一段结构化 Markdown，用户直接粘贴给 Codex 或其他 agent。

工作说明包含：

- 项目名称和项目 ID。
- 当前任务 ID、标题、目标、验收标准。
- 相关项目档案摘要。
- 相关资料文件列表。
- 当前已知风险和约束。
- 要求 agent 最后按固定格式返回工作总结。

agent 完成后，用户把总结粘贴回 ProjectFlow。ProjectFlow 解析总结，生成这些待确认建议：

- 任务状态更新。
- 新增子任务。
- 新增风险。
- 新增技术决策。
- 新增开发日志。
- 需要用户复查的文件或模块。

这是成本最低、最稳定、最不依赖外部环境的一版。

### 第二阶段：项目内 `.projectflow` 文件桥接

当第一阶段跑顺后，再让 ProjectFlow 在项目根目录生成：

- `.projectflow/agent-brief.md`
- `.projectflow/agent-result.md`
- `.projectflow/project-context.json`

用户在 agent 里可以直接读取这些文件，完成后把结果写回 `agent-result.md`。ProjectFlow 再读取并生成建议。

这个方案仍然很低成本，而且更贴近开发者文件夹工作流。

### 第三阶段：MCP 或本地 API 接入

最后再考虑让 ProjectFlow 暴露 MCP 或本地 API，让 agent 可以直接：

- 查询当前项目上下文。
- 获取当前任务。
- 提交工作总结。
- 创建待确认建议。

这一阶段体验最好，但实现成本和维护成本更高，不适合现在马上做。

## 页面结构调整

### 保留一个核心入口：项目管理

首页或主入口直接叫“项目管理”，不要再叫“总览”或“智能驾驶舱”。

项目管理页顶部应该优先展示：

- 导入项目文件夹或 ZIP。
- 当前项目选择。
- 项目资料完整度。
- AI 分析状态。
- 待确认建议数量。

项目名不是第一优先级。如果用户不填写项目名，默认使用文件夹名或 ZIP 文件名。

### 项目档案并入项目管理

项目管理页里用紧凑布局展示项目档案：

- 项目目标。
- 技术栈。
- 目录结构摘要。
- 关键模块。
- 重要约束。
- 风险。
- 决策记录。

项目档案可以是一个右侧面板、顶部标签页或可折叠区域，但不应该作为独立主导航强迫用户跳转。

### 任务看板变成 AI 协作面板

任务看板不再以“新建任务表单”为中心，而是以这些内容为中心：

- 当前推荐任务。
- 正在交给 agent 做的任务。
- agent 返回后的待确认更新。
- 已确认完成的任务。
- AI 建议的新任务和子任务。

手动新增任务仍然保留，但放成次级入口。

## Agent 连接设计

### Agent 工作说明格式

每个任务可以生成一个工作说明，例如：

```markdown
# ProjectFlow Agent Work Brief

Project: projectflow
ProjectId: 123
TaskId: PF-18
Task: 优化项目管理页的信息架构

## Goal
把项目档案、资料导入、任务建议整合到项目管理页。

## Context
- 用户希望产品面向开发者，不要商城/酒店/图书馆系统式卡片布局。
- 项目档案应并入项目管理页。
- 任务状态应尽量由 agent 工作结果回写。

## Acceptance Criteria
- 项目管理页优先展示导入项目和当前项目状态。
- 项目档案不再作为独立主入口。
- agent 工作结果能生成任务更新建议。

## Return Format
请在完成后返回 ProjectFlow Agent Result 格式。
```

### Agent 结果格式

agent 完成后返回固定格式，ProjectFlow 只解析这个格式，避免自由文本误判。

```markdown
# ProjectFlow Agent Result

ProjectId: 123
TaskId: PF-18
Status: completed

## Changed Files
- frontend/src/app/dashboard/page.tsx
- frontend/src/components/AppShell.tsx

## Summary
已将项目管理页调整为以导入项目和项目状态为核心。

## Task Updates
- PF-18: completed
- New: 补充 agent 结果导入 UI

## Risks
- 需要确认后续是否引入本地文件桥接。

## Dev Log
完成项目管理页信息架构调整。
```

### 为什么不直接自动写任务

agent 的工作总结可以很有用，但它不应该直接修改项目事实。原因是：

- agent 可能遗漏边界条件。
- agent 可能把未完成的工作描述成完成。
- 多个 agent 并行时可能产生冲突状态。
- 项目管理数据应该是用户确认后的真实状态。

所以 ProjectFlow 的角色应该是“生成建议并等待确认”，不是“自动把任务改成完成”。

## 数据和接口计划

优先复用现有 V2 数据结构，避免过早新增大量表。

### 近期可以复用

- `ProjectMaterial`：保存导入的项目资料、agent 总结文本、结构化材料。
- `AiSuggestion`：保存 AI 生成的任务更新、风险、开发日志建议。
- `ProjectMemory`：保存用户确认后的项目事实、决策和约束。
- `ProjectEvolutionRecord`：保存项目状态变化。
- 现有 `Task` 或任务模块：承接确认后的任务状态。

### 可能需要新增或扩展

后续执行时再评估是否需要轻量新增：

- `task_id`：让材料、建议和 agent 结果能挂到具体任务。
- `source_type`：区分 `PROJECT_IMPORT`、`AGENT_RESULT`、`USER_NOTE`。
- `agent_session_id`：后续如果要追踪一次 agent 工作会话，再增加。

不建议现在马上设计复杂的 agent session 系统。先把“任务 ID + 结果导入 + 建议确认”打通。

## 下一步实施计划

### 1. 信息架构收敛

- 把“项目档案”并入“项目管理”页面。
- 主导航去掉独立项目档案入口，或降级为项目管理页内部标签。
- 项目管理页顶部优先放导入项目、当前项目状态、待确认建议。
- 避免大卡片式宣传布局，使用开发工具式紧凑信息布局。

### 2. 任务看板重心调整

- 把任务看板从手动新建表单优先，改成 AI 建议和 agent 回写优先。
- 每个任务显示：
  - 当前状态。
  - 关联资料。
  - 关联 agent 工作结果。
  - 待确认建议。
- 手动新建任务保留为次级操作。

### 3. Agent 工作说明生成

- 在任务上增加“生成 Agent 工作说明”。
- 工作说明先做成可复制 Markdown。
- 内容来自项目档案、任务、资料摘要和用户确认过的记忆。
- 不依赖 mock，不需要外部插件。

### 4. Agent 结果导入

- 增加粘贴 Agent Result 的入口。
- 解析固定 Markdown 格式。
- 把结果转换为 `AiSuggestion`，包括任务状态、子任务、风险和开发日志。
- 用户确认后再写入真实任务、项目记忆和开发日志。

### 5. `.projectflow` 文件桥接

- 第一阶段稳定后，再支持导出和读取 `.projectflow` 文件。
- 这一步可以进一步减少复制粘贴。
- 仍然保持用户确认机制。

### 6. 最终联调和测试

- 当前先不做大范围测试，避免在流程未定型时浪费时间。
- 实施过程中只做必要的静态检查、类型检查或局部编译，确保不引入明显错误。
- 等页面结构和 agent 闭环稳定后，再做完整前后端测试。

## 验收标准

- 用户进入产品后第一眼看到的是项目导入和当前项目管理状态，不是项目宣传卡片或模板展示。
- 项目档案在项目管理页内可见，并能影响任务建议。
- 任务看板能接收 agent 工作结果生成的建议，用户不需要大量手动填写任务。
- agent 与 ProjectFlow 的连接至少能通过复制粘贴 Markdown 闭环跑通。
- 所有 AI 或 agent 生成的状态变化都需要用户确认。
- UI 视觉接近开发工具和后台工作台，避免商城、酒店预订、图书馆管理系统式布局。
- 代码实现时优先复用现有实体、接口和页面结构，不引入无必要的新系统。

## 暂不做

- 不做商城式模板中心。
- 不做宣传型首页。
- 不做自动无确认改任务状态。
- 不做复杂插件市场。
- 不做 GitHub App 级别集成。
- 不做浏览器扩展。
- 不做常驻本地 daemon。

这些都可以等核心闭环跑通后再评估。
