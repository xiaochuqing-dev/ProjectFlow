# ProjectFlow V3 最终开工指南

日期：2026-06-07

## 1. V2 当前不足

V2 已经完成了基础能力：项目 zip 导入、DeepSeek / OpenAI-compatible 配置、`.projectflow` 协议写入、agent result 扫描、待确认建议、项目记忆和成果输出雏形。

但从真实用户视角看，V2 仍然像一个功能拼装出来的流程页，还没有形成“开发者工具”的产品感。

### 1.1 首页缺少主线

当前首页最大的问题不是功能少，而是卡片太散。

用户进入后看到的是：

- 导入完整项目。
- Agent 写回协议。
- 任务队列。
- 项目档案 / 初始分析。
- 待确认建议。
- 当前项目。
- 最近材料。
- 最近演进。

这些区块各自有意义，但组合起来没有形成明确工作流。用户除了导入 zip 之后能看到一点反馈，其他卡片不知道要做什么，点完也不像真的推进了项目。

V3 必须从“功能卡片集合”改成“项目工作台”。

### 1.2 任务、日志、成果页面太像为了流程而流程

任务页现在更像普通看板：点一下开始，再点一下下一步，再点一下完成。

这个反馈对开发者价值不高，因为它没有回答：

- agent 为这个任务实际做了什么？
- 哪些文件发生变化？
- 有没有测试或构建证据？
- 这个任务沉淀了什么经验？
- 它对项目事实产生了什么影响？

开发日志页和成果输出页也有类似问题。它们像是单独存在的流程页面，而不是围绕真实开发过程自动整理出来的资产。

### 1.3 可编辑性不足

V2 的项目档案、建议、日志、成果更多是展示和采纳，缺少可编辑性。

项目管理不应该只是“AI 生成一段分析，然后用户采纳”。开发者需要能够直接修正：

- 项目定位。
- 当前阶段。
- 技术栈。
- 关键模块。
- 已完成能力。
- 当前风险。
- 技术决策。
- 下一轮目标。
- 错误或重复的 AI 判断。

如果用户无法编辑，ProjectFlow 就只是摘要工具，不是项目管理工具。

### 1.4 视觉反馈不专业

当前有些展示方式不适合产品化，例如深色命令行式的结构摘要。

问题是：

- 看起来像原始终端输出。
- 路径过长，阅读负担高。
- 没有模块分组。
- 没有解释这些文件对项目有什么意义。
- 占用视觉重量，但给用户的反馈价值不高。

V3 应该把“目录树展示”升级成“项目结构理解”。

### 1.5 API 配置没有充分变成产品价值

DeepSeek / OpenAI-compatible 配置能带来一点交互感，但目前还没有充分服务核心流程。

模型 API 不应该只是“可配置”。它应该真正参与：

- agent result 二次总结。
- 今日变化归纳。
- 大变化 / 小变化识别。
- 技术经验提炼。
- 项目事实更新建议。
- 简历描述、周报、README、复盘材料生成。

## 2. V3 核心目标

V3 的目标不是增加更多页面，而是重构 ProjectFlow 的产品重心。

核心定位：

```text
agent 负责改进项目。
ProjectFlow 负责记录改进、审查变化、沉淀项目事实，并把开发过程转化为数字化资产。
```

V3 要让用户第一眼就明白：

- 当前项目相比一开始发生了什么变化。
- 今天 agent 做了哪些真实工作。
- 哪些变化需要用户确认。
- 哪些经验、风险、决策已经沉淀。
- 这些信息后续可以生成什么成果。

ProjectFlow 不做通用项目管理后台，不做商城式首页，不做酒店或图书馆管理系统风格。它应该是开发者工作台。

## 3. 真实使用场景

目标用户每天可能同时推进多个实用项目，有大项目，也有小项目。

一个典型场景：

```text
用户早上开始工作，让 Codex 或其他 agent 帮忙改几个项目。
中途或者晚上想打开 ProjectFlow 看看：
今天到底做了什么？
项目相比一开始发生了哪些变化？
哪些是小修小补？
哪些是关键能力推进？
有哪些技术经验或决策值得沉淀？
这些变化能不能转成周报、README、简历描述或项目复盘？
```

这才是 ProjectFlow 应该解决的问题。

因此，V3 的反馈不应该来自用户手动点任务状态，而应该来自真实开发痕迹：

- agent 输出。
- 文件变化。
- 任务证据。
- 测试或构建结果。
- 技术决策。
- 风险变化。
- 用户确认记录。
- 项目事实变化。

## 4. Agent 与 ProjectFlow 的分工闭环

V3 的关键是让 agent 和 ProjectFlow 无缝配合。

### 4.1 分工

agent：

- 理解用户需求。
- 修改真实项目代码。
- 运行测试或给出验证说明。
- 按协议写回结构化 result。

ProjectFlow：

- 读取 agent result。
- 结合项目历史、项目事实、任务、材料进行分析。
- 用模型 API 做二次总结和分类。
- 生成待确认变化。
- 让用户编辑、采纳、忽略或合并。
- 把确认后的信息写入项目事实、每日回顾和成果素材。

### 4.2 最小闭环

V3 的最小闭环应该是：

```text
1. ProjectFlow 写入 .projectflow 协议。
2. 用户在 agent 里自然描述需求。
3. agent 改项目并写回 .projectflow/inbox 或任务 result。
4. ProjectFlow 扫描 result。
5. ProjectFlow 用模型 API 总结变化、风险、决策、经验和成果素材。
6. 用户在 ProjectFlow 中确认。
7. 确认内容进入项目事实、每日回顾、任务证据和成果输出。
```

### 4.3 模型 API 的作用

模型 API 不应该只是生成一段普通复盘。

它应该用于：

- 判断本次变化是大变化还是小变化。
- 判断哪些变化影响项目定位。
- 提炼技术决策。
- 提炼经验积累。
- 总结风险和后续动作。
- 对比项目初始状态和当前状态。
- 生成可编辑的成果草稿。

用户确认之前，模型只提出建议；用户确认之后，才进入正式项目资产。

## 5. 数字化资产沉淀

V3 要把开发过程沉淀成可复用资产。

这些资产包括：

- 项目事实：项目定位、阶段、技术栈、模块、能力、风险、决策。
- 每日变化：今天做了什么、大变化、小变化、未完成点。
- 任务证据：任务目标、验收标准、关联 result、文件变化、测试证据。
- 技术决策：为什么这么做、取舍是什么、后续影响是什么。
- 风险与解决过程：发现的问题、解决方式、仍需关注的点。
- 经验总结：开发者今天从项目中积累了什么。
- 成果素材：README、周报、项目复盘、简历描述、作品集描述。

成果输出不应该凭空生成，而应该基于已确认资产生成，并能追溯来源。

## 6. 全站信息架构重构

当前导航是：

```text
项目管理
任务
开发日志
成果输出
个人设置
```

V3 建议改成：

```text
工作台
变更审查
项目事实
每日回顾
成果输出
设置
```

### 6.1 工作台

第一屏回答三个问题：

- 今天发生了什么？
- 哪些变化等待确认？
- 下一步最值得处理什么？

工作台不再堆卡片，而是围绕真实状态组织：

- 顶部：项目选择、本地路径、agent 连接状态、关键动作。
- 中间：当前项目事实摘要和今日变化摘要。
- 右侧：待确认变化和下一步动作。
- 次要信息：改成长条入口或折叠区。

### 6.2 变更审查

集中处理 agent result、zip 导入差异、材料更新带来的变化。

每条变化都应该能：

- 查看来源。
- 编辑内容。
- 采纳。
- 忽略。
- 合并到已有项目事实。
- 绑定到任务或每日回顾。

### 6.3 项目事实

项目事实是长期档案，不是只读分析。

必须支持编辑：

- 项目定位。
- 当前阶段。
- 技术栈。
- 关键模块。
- 已完成能力。
- 当前风险。
- 技术决策。
- 下一步目标。
- 可展示成果。

每个字段应标记来源：用户手动、zip 分析、agent 写回、模型总结、建议采纳。

### 6.4 每日回顾

开发日志升级为每日回顾。

每日回顾不靠用户手写，而是从这些来源汇总：

- agent result。
- 任务变化。
- 文件路径变化。
- 用户采纳记录。
- 项目事实变化。
- 模型 API 总结。

用户可以编辑后保存为当天记录。

### 6.5 成果输出

成果输出基于已确认项目资产生成：

- 周报。
- README 更新草稿。
- 简历项目描述。
- 项目复盘。
- 作品集素材。
- 下一阶段计划。

输出内容应显示来源，用户可以继续编辑。

### 6.6 设置

设置集中放置：

- DeepSeek / OpenAI-compatible 配置。
- 模型测试。
- `.projectflow` 协议规则。
- 本地路径偏好。
- 后续桌面端 / helper 配置。

## 7. 页面交互重构方向

### 7.1 首页不再堆卡片

首页要减少普通卡片。

重要内容做成可编辑、可审查的主区域；次要内容做成长条入口：

```text
[ 今日 agent 写回 3 条，需要审查 ]        进入
[ 已连接 .projectflow，暂无新 result ]    查看
[ 今日变化 18 个文件，2 条测试证据 ]      生成回顾
[ 发现 2 条可沉淀经验 ]                  确认
```

点击后进入集中详情页，详情页提供返回按钮。

### 7.2 卡片颜色与层级

后续仍然可以使用卡片，但不能所有卡片都一样。

建议：

- 关键待处理：浅蓝或浅橙，强调需要用户动作。
- 已确认事实：浅绿或白底，强调稳定状态。
- 历史材料：浅灰，降低视觉权重。
- 风险问题：浅红，但只用于真正需要注意的内容。
- 普通入口：长条矩形，不做大卡片。

颜色只用于区分交互状态，不做装饰。

### 7.3 结构摘要改成项目结构理解

不要在首页展示深色命令行大块。

改成：

- 模块分组：frontend、backend、docs、config、scripts。
- 每组显示关键文件和文件数量。
- 高亮 README、测试、启动脚本、部署配置、agent 协议。
- 长路径默认折叠。
- 点击进入结构详情页。

首页只回答：

```text
项目有哪些主要模块？
哪些资料已经识别？
哪些关键资料缺失？
```

### 7.4 任务页改成任务证据页

任务不再只是状态流转。

任务详情应展示：

- 任务目标。
- 验收标准。
- 关联 agent result。
- 涉及文件。
- 相关风险。
- 相关决策。
- 测试或构建证据。
- 下一轮 agent brief。

用户看到的不是“点下一步”，而是“这个任务为什么存在、agent 做了什么、是否有证据证明完成”。

### 7.5 开发日志改成每日回顾

每日回顾应回答：

- 今天做了什么？
- 哪些是大变化？
- 哪些是小变化？
- 产生了什么经验？
- 有哪些风险和决策？
- 哪些项目事实被更新？
- 明天应该继续什么？

### 7.6 成果输出可追溯

成果输出页应展示：

- 生成内容。
- 来源引用。
- 可编辑正文。
- 可复制 / 导出。
- 可回写到项目资产。

## 8. V3 开工阶段

### Phase 1：重构导航和首页工作台

目标：先解决第一眼看不出亮点、卡片堆叠、反馈空洞的问题。

工作项：

- 导航改为工作台、变更审查、项目事实、每日回顾、成果输出、设置。
- 首页改成工作台结构。
- 去掉低价值大卡片。
- 次要信息改成长条入口。
- 结构摘要改为模块化项目结构理解。

### Phase 2：项目事实可编辑

目标：让 ProjectFlow 从展示分析结果变成维护项目事实。

工作项：

- 项目定位、阶段、技术栈、能力、风险、决策、下一步目标可编辑。
- 保存到 Project Memory。
- 标记字段来源。
- 用户确认内容优先级高于 AI 推断。

### Phase 3：Agent Result 变更审查

目标：把 agent 写回内容变成真正的变更审查。

工作项：

- 扫描 `.projectflow` result。
- 拆分为完成内容、文件变化、任务变化、风险、决策、经验、成果素材。
- 每条可编辑、采纳、忽略、合并。
- 采纳后进入项目事实和每日回顾。

### Phase 4：每日回顾与经验沉淀

目标：解决“我今天做了这么久，到底改变了什么”的问题。

工作项：

- 按日期汇总 agent result、项目事实变化、任务证据和用户确认记录。
- 用模型 API 生成每日总结草稿。
- 区分大变化、小变化、经验、风险、明日建议。
- 用户可编辑保存。

### Phase 5：成果输出升级

目标：把项目过程资产转成可展示内容。

工作项：

- 基于已确认事实和每日回顾生成周报、README、简历描述、项目复盘。
- 每段内容显示来源。
- 支持编辑、复制、导出。

### Phase 6：桌面端 / Tauri helper

目标：补足 Web 端本地文件能力。

建议先做轻量 Tauri helper，而不是完整重做桌面端。

helper 负责：

- 选择项目文件夹。
- 监听 `.projectflow`。
- 自动发现新 result。
- 检查本地服务状态。
- 必要时启动本地服务。

## 9. 验收标准

V3 第一阶段完成后，应满足：

- 用户进入首页第一眼能看懂当前项目状态。
- 用户知道今天发生了什么、等待确认什么、下一步做什么。
- 首页不再是同质化卡片堆叠。
- 任务不再只是点击推进状态，而是有真实开发证据。
- 开发日志方向明确升级为每日回顾。
- 成果输出明确基于已确认资产生成。
- agent 与 ProjectFlow 的分工清晰：一个改项目，一个记录和沉淀。
- DeepSeek / 模型 API 真正参与总结、经验提炼和成果生成。
- 次要信息通过长条入口进入详情页，不抢主区域。
- UI 风格务实、清晰、开发者工具化，不像商城、酒店后台、图书馆系统或宣传页。

如果用户还需要在一堆卡片里找功能，或者点完按钮仍然不知道项目发生了什么变化，V3 就没有成功。
